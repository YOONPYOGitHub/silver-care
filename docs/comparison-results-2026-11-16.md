# 네 서비스 비교와 자원 격리 후 지연

측정일: 2026-11-16. 현재 구성은 [아키텍처](architecture.md), 배포 방법은 [운영 절차](operations.md)에 있다.
**자원 격리 후 공개 URL 측정·2번 backend 평가와 격리 전 평가를 구분한다.**
아래 수치는 휴대폰 실행 성능이나 임상적 안전성 인증이 아니다.
표와 기록의 4번 `/qwen-azure-rag/`는 측정 당시 주소다. 현재 공개 경로는 `/qwen-rag/`이며
이전 주소의 별칭·호환 리디렉션은 제공하지 않는다. 주소 변경을 새 성능 측정으로 취급하지 않는다.

## 1. 적용 범위

네 URL과 앱 이미지·프론트엔드를 유지했다. 추가 양자화·후보 축소·문맥 절단·모델 교체는 적용하지 않았다.

| 버전 | 경로 | 전용 CPU pool | 모델·Speech 계정 | 검색 |
| --- | --- | --- | --- | --- |
| 1. Azure 기준 | `/` | `azurecpu`, D2ds_v5 ×1 | `ondam-v1-e4b60458` | 전용 Azure Search `silvercare-v1-e4b60458` |
| 2. Qwen + 자체 RAG | `/local-rag/` | `localmem`, D8ds_v5 ×1 | `ondam-v2-e4b60458` | 기존 OpenSearch + BGE FP32 |
| 3. Qwen 단독 | `/local-only/` | `onlycpu`, D2ds_v5 ×1 | `ondam-v3-e4b60458` | 없음 |
| 4. Qwen + Azure RAG | `/qwen-azure-rag/` | `qwazcpu`, D2ds_v5 ×1 | 기존 `ai-foundry-m098047` | 기존 `silvercare-rag-2a5aalbg7ugfc` |

4번이 사용하던 Qwen 생성·OpenAI 임베딩·Search·Speech와 할당량은 유지했다.
다른 버전을 별도 계정·배포로 이동했다. 1번 Search는 스키마와 13,324개 문서의 모든 필드·ID를 검증해
복제했다. 원래 512차원 문서 벡터 캐시를 재사용해 새 임베딩 생성은 0건이다.
2번의 새 Qwen 임베딩과 기존 OpenSearch 문서 벡터의 단일 표본 cosine은 0.99999768이었다.
동일 모델 버전의 호환성 확인이지 모든 벡터의 bit 단위 동일성 증명은 아니다.

서비스별 관리 ID·ServiceAccount·NetworkPolicy를 사용한다.
2번에서 4번으로 보낸 실제 요청은 모델 HTTP 401, Search HTTP 403으로 거부됐고,
4번 내부 gateway TCP 연결은 차단됐다. 네 서비스 모두 정책 적용 후 실제 답변·MP3 TTS·WAV STT를 통과했다.
기존 공용 gateway와 공용 ID의 두 AKS federated credential은 폐기했다.
공유 구성을 재생성하는 기존 배포 명령도 클러스터 marker로 차단한다.

공통 HTTPS 진입점·AKS 기반 시설/DNS·ACR·질병관리청 외부 API와 서비스키·구독/공급자 전체 한도는 예외다.
이는 서비스 사이 실행 자원의 분리이며 모든 종류의 부하에서 영향이 절대 없다는 보장은 아니다.

**비용:** Qwen용 A100 80GB는 생성 3개 + 2번 임베딩 1개, 합계 4개다.
이전의 사용하지 않는 Qwen 임베딩 GPU는 이전 확인 후 삭제했다.
임시 평가 `evalcpu` pool·평가 서버는 삭제했고 검색 데이터와 롤백/결과 보관 PVC는 유지했다.

## 2. 자원 격리 후 실제 지연

같은 공개 HTTPS 호스트에서 합성 질문을 순차 전송했다.
서버를 재시작한 후 정상 startup warmup 1쌍만 캐시에 있는 상태에서 시작했다.
반복은 같은 질문의 재요청이며, 답변을 저장해 반환하는 캐시는 아니다.

| 2번 질문 | 최초 처리 | 같은 질문 재요청 |
| --- | ---: | ---: |
| 기본 생활·건강 카드 | **92.520초** | **6.408초** |
| 기초연금 신청·서류 | 56.147초 | 4.739초 |
| 집에서 자주 넘어지는 아버지의 낙상 예방 | 129.669초¹ | 7.720초 |

¹ 낙상 최초 값만 같은 운영 이미지·설정의 Pod 내 직접 호출 진단이다.
공개 TLS API와 구분하며 HTTP 구간별 시간을 수집했다. 재요청은 공개 URL이다.
표본이 작으므로 이 표로 p95·평균 사용자 지연·일반적인 속도 향상률을 추정하지 않는다.

기본 카드의 실제 질문은 “건강하게 지내려면 오늘 무엇부터 해보면 좋을까요?”다.
최초 처리에서 새로운 query/text 145쌍을 계산했다.
재요청 시 캐시 hit는 9→163으로 증가했지만 실제 추론 쌍 수는 146→146으로 동일했다.
**반복 질문이 빠른 것은 기존 score cache 효과이며, 새로운 질문의 병목이 해결된 것은 아니다.**
LRU는 2,048쌍으로 제한돼 있고 다양한 질문을 계속 받으면 결과는 달라질 수 있다.

### 2번이 처리 중일 때 4번

동일한 기본 건강 질문을 사용했다. 모두 HTTP 200이며 정상 출처 4개를 반환했다.

| 시점 | 4번 공개 URL 응답 |
| --- | ---: |
| 2번 부하 전 | 9.286초 |
| 2번의 92.520초 처리와 겹치는 요청 | **6.897초** |
| 2번 진단 후 | 6.517초 |

이번 단발 동시 요청에서는 4번의 지연 증가가 관측되지 않았다.
차이를 통계적 개선이나 모든 동시 사용자 수에 대한 보장으로 해석하지 않는다.
동일 질문의 별도 공개 smoke는 1번 5.499초, 3번 4.719초였다.
버전별 문장 길이·출처·답변 내용이 달라 순수한 모델 토큰 생성 속도 비교는 아니다.

### 2번 낙상 진단의 구간

| 구간 | 관측 |
| --- | --- |
| Qwen 검색어 확장 | 1.297초 |
| Qwen 질문 임베딩 | 1.141초 |
| 개별 OpenSearch 요청 | 0.013–0.026초 |
| BGE `/rerank` 4회 | 64·64·20·31쌍, 개별 HTTP 37.460–83.066초 |
| Qwen 최종 생성 | 6.300초 |
| 전체 | 129.669초 |

재정렬 HTTP 요청은 서로 겹치고 단일 모델 lock의 대기도 포함한다. 네 HTTP 시간을 합하면 안 된다.
전체 시간에서 생성·임베딩·검색을 제외하면 약 120초가 재정렬 구간에 해당한다.
측정 도중 재정렬 Pod는 약 3.93 CPU를 사용했고 다른 2번 Pod는 각각 0.04 CPU 미만이었다.
**서비스 간 공유가 아니라 2번 자체의 CPU BGE 계산이 주 병목이다.**

## 3. 추가 개선 방향 — 미적용

| 우선 검토 | 방향 | 조건·한계 |
| --- | --- | --- |
| 1 | 같은 BGE checkpoint를 2번 전용 GPU runtime에서 실행 | 큰 가속 가능성을 검증할 첫 후보. 4번 GPU는 사용하지 않는다. 현재 Foundry template에 임의 reranker를 추가할 수 있다고 가정하지 않으며 별도/커스텀 배포 지원과 비용을 먼저 확인한다. |
| 2 | 더 큰 전용 CPU와 적절한 ONNX thread 설정 비교 | 모델·정밀도 유지가 가능하지만 비용 증가 대비 개선 폭은 실측해야 한다. node만 늘리고 기존 6-thread 설정을 유지하는 것으로 큰 가속을 보장하지 않는다. |
| 3 | INT8 예비 점수 + 필요한 후보의 FP32 재확인, 또는 더 작은 multilingual reranker | CPU 비용 절감 후보지만 순위·한국어 의료 근거 회수에 대한 재평가가 필요하다. 승인 없이 기본 경로에 적용하지 않는다. |

이전 INT8 시험은 동결된 RRF 상위 12개 후보 ×46문항에서 평균 점수 계산 약 3.08배 가속을 보였으나,
MRR이 0.637681→0.626812로 0.01087 하락해 사전 한도 0.01을 넘었다.
Hit@6은 양쪽 32/46이지만 **품질 기준을 통과한 것으로 취급하지 않고 FP32를 유지했다.**
이 시험은 전체 공개 API의 3배 가속이나 의료적 동등성 증거가 아니다.

후보 수 축소·본문 절단·재정렬 제거는 기능과 근거 회수의 변경을 숨길 수 있어 기본 제안에서 제외한다.
새 최적화는 지연뿐 아니라 동일 후보의 순위·전체 검색·답변 근거·의료 필수 항목을 함께 검증해야 한다.
현재 빠른 UI·기능 확인에는 4번을 계속 사용하고 2번은 별도의 성능 검토 대상으로 유지할 수 있다.

## 4. 네 버전 품질 평가

의료 평가와 1·3·4번 backend 평가는 격리 전에 별도 D8ds_v5 CPU 복제본에서
당시 실제 운영 이미지로 수집했다. 중지했던 2번 backend 세트는 자원 격리 후 별도 D8ds_v5에서
같은 운영 이미지·FP32 재정렬 이미지·6-thread 설정·동결된 평가 코드와 데이터로 완료했다.
2번 전용 생성·임베딩·OpenSearch와 평가 전용 재정렬만 사용했으며 4번으로 평가 요청을 보내지 않았다.
이 절의 지연은 공개 TLS 지연이 아니며 위 공개 측정과 하나의 평균으로 합치지 않는다.
문항·답변을 새로 생성해 실패를 대체하지 않았다.

### 독립 근거 기반 의료 평가

각 버전 24건 모두 API 답변을 반환했다. 공통 고정 응급 답변 4건은 모델 비교에서 제외해
각 20건·필수 명제 51개를 같은 참조 범위에서 비교했다.
judge는 `gpt-6-astra`, version `2026-09-03`이다.
질문 dataset SHA256은 `e6241d1b1926ff6412d2b471c883a2642e7762f544fe27882b7694167e4d2c66`이다.

| 버전 | 필수 명제 완전 충족 | pass / partial / needs_review / fail / unsafe | 내부 API 중앙값 / p95 |
| --- | ---: | --- | --- |
| 1 | 43/51, 84.3% | 3 / 1 / 15 / 0 / 1 | 8.883 / 13.846초 |
| 2 | 31/51, 60.8% | 1 / 0 / 8 / 3 / 8 | 127.000 / 150.930초 |
| 3 | 27/51, 52.9% | 0 / 0 / 11 / 0 / 9 | 4.881 / 6.959초 |
| 4 | 32/51, 62.7% | 0 / 0 / 12 / 0 / 8 | 7.218 / 8.459초 |

**이는 임상 전문가가 검증한 정확도나 안전성 비율이 아니다.**
`needs_review`는 제공된 근거 발췌로 추가 주장을 판단하기 어려운 경우 등을 포함하며 오답과 동일하지 않다.
`unsafe`는 중요 필수 명제의 누락·부분 충족·모순 또는 금지 항목 검출에 대한 보수적 자동 flag다.
전문가가 실제 위해를 확인했다는 뜻이 아니지만 의료 서비스 출시 전에 검토해야 할 결과다.
필수 명제 충족률 하나만으로 위 flag를 무시하거나 4번을 임상적으로 검증됐다고 결론 내리지 않는다.
합성 calibration 12/12 일치는 임상 인증이 아니다. 1번의 judge 형식 오류 1건만 동일 답변으로 재채점했다.

### 완료한 backend 회귀 평가

| 버전 | 전체 retrieval Hit@6 | MRR@6 | 필수 검색 목표 충족 | audience 규칙 통과 | detail 규칙 통과 |
| --- | --- | ---: | --- | --- | --- |
| 1 | 43/46 | 0.8188 | 통과 | 32/32 | 3/3 |
| 2 | **40/46** | **0.7406** | **미통과** | **27/32** | **2/3** |
| 3 | 해당 없음 | 해당 없음 | 해당 없음 | 26/32 | 0/3 |

전체 세트의 실행과 결과 보관을 완료했다. **완료는 모든 품질 기준 통과를 뜻하지 않는다.**
2번의 keyword Hit@6은 24/46, hybrid는 40/46이고 검색 기술 오류는 양쪽 모두 0건이다.
hybrid 평균은 약 106.226초로, 앞서 관측한 CPU 재정렬 병목과 일치한다.
복합질환 목표 설정·욕창 드레싱 근거·반복 저혈당 문항의 필수 목표를 회수하지 못해
2번의 `required_targets_passed`와 종합 `nonregression_passed`는 **false**다.
전체 Hit@6 증가만으로 이 필수 회수 기준을 통과한 것으로 취급하지 않는다.
4번도 욕창 상태 기록·복합질환 목표 설정·욕창 드레싱 문항의 필수 목표를 회수하지 못해
해당 기준과 종합 검색 비회귀 기준을 통과하지 못했다. 1번은 두 기준을 통과했다.

audience 32건 중 실제 답변 생성은 1·2·3번 각각 31건, 4번 32건이다.
1번의 1건은 문항에서 명시적으로 허용한 제공자 안전상 거절이다.
2번은 `switch-to-self`에서 모델 HTTP 503 1건, 3번은 `kdca-fall-prevention`에서 모델 HTTP 502 1건이
발생했다. 두 기술 실패를 재시도 성공으로 바꾸거나 분모에서 제외하지 않았다.
2번의 나머지 audience 미통과는 길이 제한·필수 출처·문의 대상 누락이며,
detail 미통과 1건은 간단한 연락처 질문의 길이 제한 위반이다.

3번의 검색·근거 검사는 0점이 아니라 해당 없음이다. detail 미통과는 연락 대상·개념 누락 등
적용 가능한 내용 검사이며 검색하지 않는 모델에 가짜 출처를 요구한 결과가 아니다.
규칙 통과율은 임상 정확도가 아니다. 평가 방법·제약은 [평가 도구](../evaluation/README.md)에 있다.

모든 원시 결과와 입력 hash를 기존 결과 보관 PVC 및 운영자 전용 로컬 archive에 보관했다.
평가 Pod·결과 추출 Pod·임시 `evalcpu` node pool은 삭제했다.
서비스의 모델·이미지·알고리즘은 이번 평가 완료를 위해 변경하지 않았다.
정리 후 4번 공개 URL에서 실제 기본 건강 질문을 다시 확인했고 HTTP 200·출처 4개·6.716초로 응답했다.
